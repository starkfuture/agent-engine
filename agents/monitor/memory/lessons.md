- Impact wording must match the evidence, in the impact field and everywhere else. Ready pods alone support only "pods ready", never "availability preserved": that needs a passing end-to-end check, and no tool here runs one. Ready pods plus traffic and error rates that hold steady against 1 day and 7 days ago support "no customer impact observed". A failing check (pods still not ready after a rollout, a journey still failing) means "availability NOT confirmed".
- Never upgrade the impact phrase. If part of the evidence is missing (a service with no traffic or error-rate series, a blind source), use the weaker phrase, name what you could not measure and list it in not_checked. "unknown" beats a phrase the evidence does not support.
- Fail-closed boot: a deploy looks fine, then CrashLoopBackOff whose log ends in one throw line about a missing required setting (for example OUTBOX_ROUTE_*, S2S_SECURITY_TOKEN, DATABASE_URL, or CORS_ALLOWED_ORIGINS when NODE_ENV=production), often right after migrations ran. The fix is the config plus a restart a human performs. A rollback is usually wrong: rolling back the image does not add the missing key. Quote the throw line and name the key.
- Database grant, ownership and migration-order errors are not an infrastructure outage, and neither a restart nor a rollback fixes them: "permission denied for schema/table/relation", "must be owner of", "role ... does not exist", "no pg_hba.conf entry", "relation ... does not exist", "too many connections". They often follow a clean migration step. Suggest the grant, owner, access-rule or migration-order fix, and rate severity by what customers see.
- CORS can be set but wrong: the service is healthy, its logs are clean, and browsers are still blocked. Server metrics may look normal; at most the browser's real requests drop while preflight (OPTIONS) requests continue. A wrong origin, method or header each needs its own config fix, and a rollback fixes none of them. If no tool shows the browser side, say so in not_checked.
- Signing-key drift shows as 401s, not 5xx. A 401 rise on several services at once points at token verification (issuer, audience or signing keys), not at each service's code. A brief 401 bump right after the signing keys (JWKS) rotate is expected while verifiers refetch them; 401s that persist after it point at a stale key cache. An empty key set is critical: no token can be verified.
- A missing series is not a healthy one. No series, no log lines or an empty result can mean the exporter, scrape or labels changed, not that nothing is wrong. Before reading silence as "no errors" or "all ready", make sure the base series exists, for example the service's request counts (service_overview shows them). If it does not, say that source was blind for the check and list it in not_checked.
- When a tool result shows firing Prometheus alerts, treat them as context, not proof of cause: an alert says a watched condition holds, not why. Confirm the mechanism with metrics, logs or traces before naming a cause.
- Before calling a trace row latency, background polling or noise, look at its errors: run trace_search with { rootName = "<its operation>" && status = error } (name = skips errors below the root), narrow it with kind = client, and read the service's error logs at those times. Unfiltered samples, durations and a clean inbound HTTP table do not count: failing outbound calls never show in the inbound table. Propose no noise rule for a trace row unless that evidence shows an expected outcome.
- Error traces bunched at fixed clock times (:00, :15, :30, :45) with near-identical durations point at a scheduled job whose calls time out: check what the job calls before suspecting the service's own database. If the error-trace count jumps while the matching HTTP status counts stay flat, the jump is unexplained: say so in not_checked instead of citing the flat HTTP counts as the explanation.
